# SPECS — 10.6 WebSocket chat streaming

Claire Whitfield’s staff get the compliance answer in one shot. Stream `compliance_assistant` token by token, and let the staff member interrupt that reply and redirect it on the same connection.

Authoritative domain: [`context/10.6_CONTEXT.md`](../context/10.6_CONTEXT.md). Do not edit `context/**`. Chat names come from that file. Do not copy Part 1 RFP fields (`ticket_id`, `rfp_id`, `client_name`, `rfp_ticket_created`) into any chat frame. No patient identifier in any frame, log, or stored message. The speaker is internal staff.

**Out of scope:** a new agent, tool or memory changes, LangGraph `interrupt()` / HITL resume, Redis, a second app, closing the session, and any RFP route.

**Read:** `services/api/agent/router.py`, `services/api/agent/chat.py`, `services/api/agent/graph.py` (`desk_graph`), `data/pipelines/rag.py` (`generate_answer`), `uis/backoffice/components/knowledge/DeskKnowledgePage.tsx`.

## 1. Why not LangGraph `messages` mode

`generate_policy` calls `generate_answer`, which returns one string. `desk_graph.astream(..., stream_mode="messages")` emits nothing from that call. `values` and `updates` emit a node dict only after the node returns. Do not add a second model client.

Keep `generate_answer(question, context) -> str` for `POST /agent/query`, `POST /knowledge/query`, and existing tests. When a stream sink is set, that same function posts `"stream": true` and yields `choices[0].delta.content`. A cancel flag closes the HTTP response and returns the text received so far. No sink: the blocking call.

Abort means cancel that HTTP stream and the generation task. Do not call LangGraph `interrupt()`.

## 2. Session and fan-out

**ChatSession:** `session_id`, `agent_id` (`compliance_assistant`), `user_id` (the JWT user), `status` (`active` or `interrupted`), `created_at`. Do not set `closed`.

One channel per session, `chat.<session_id>`: one producer, N subscriber queues, in this process. A second socket receives the same frames and does not start a second graph run.

`POST /agent/query` stays request/response. The socket is `WS /agent/chat` on the same router.

| | |
| --- | --- |
| URL | `WS /agent/chat?session_id=<id>&token=<jwt>` |
| Auth | Same JWT as `get_current_user`. Query `token`, or a first frame `{"event":"auth","data":{"token":""}}`. Close before any chat frame if it is missing or invalid. |
| Bind | `session_id` is required. Unknown id: empty snapshot, `status` `active`, `user_id` from the token. |

If a checkpoint config is passed, `thread_id` is `session_id`. Do not `Command(resume)` an aborted turn. The next user text is a new assistant message. `session_snapshot` is the record reconnect restores, not a replay of the graph.

A generation in progress sets the session to `interrupted` only for that aborted reply’s message. The next `user_message` or `interrupt_requested` with `new_input` sets the session back to `active` and starts a new assistant `message_id`. Do not delete the interrupted message.

## 3. Frames

JSON text frames. `event` plus `data`. Do not use a top-level `type`.

Client:

```json
{"event":"user_message","data":{"session_id":"","text":""}}
{"event":"interrupt_requested","data":{"session_id":"","new_input":""}}
```

`user_message` while a generation is running is an `interrupt_requested` whose `new_input` is that text.

Server:

```json
{"event":"session_snapshot","data":{"session_id":"","messages":[{"message_id":"","role":"user","text":"","status":"completed"},{"message_id":"","role":"assistant","text":"","status":"interrupted"}]}}
{"event":"token_chunk","data":{"session_id":"","token":"","sequence":1}}
{"event":"generation_interrupted","data":{"session_id":"","message_id":"","status":"interrupted"}}
{"event":"generation_completed","data":{"session_id":"","message_id":""}}
```

Send `session_snapshot` immediately after auth, before any live token. `token` is a delta. `sequence` starts at 1 for each generation and increases by 1. The client appends tokens to the open assistant message.

On abort: no further `token_chunk` for that generation, store the partial text, `generation_interrupted` with that `message_id`. Non-empty `new_input` is the next user turn and a new assistant `message_id`.

`generation_completed` only if the task finishes. The snapshot stores the graph’s final answer (after `guard_output`). If that string differs from the concatenated tokens, `generation_completed.data` also includes `text` and the client replaces the live bubble. Otherwise omit `text`.

## 4. Desk page

`DeskKnowledgePage` does not use `POST /api/knowledge/query` for this screen. Open `WebSocket` to the API (`NEXT_PUBLIC_API_WS_URL`, default `ws://127.0.0.1:8000`) at `/agent/chat`. Token from `getToken()` on the query string. `session_id` is a UUID kept in `sessionStorage`.

Show a transcript. Append each `token` as it arrives. Sending while a reply is in progress sends `interrupt_requested` with that text as `new_input`. The partial bubble stays, marked interrupted. The next assistant bubble is a new message.

On close: keep the transcript, show **Reconnecting…**, wait 1s, 2s, 4s, 8s, 16s, then 30s. A successful open resets the delay. The server’s `session_snapshot` replaces the transcript before any new `token_chunk`.

## 5. Tests

`tests/pipelines/test_agent_ws.py`. No live model: a fake sink yields a few tokens and stops when cancel is set.

- No token: the socket closes before a chat frame.
- One `user_message`: at least one `token_chunk` (`token`, `sequence`), then `generation_completed` with a `message_id`.
- `interrupt_requested` mid-stream: no further `token_chunk` for that generation; `generation_interrupted` with `status` `interrupted`; a following `new_input` produces a different `message_id`.
- Two sockets, one `session_id`: both receive the same chunks; the generator runs once.
- Reconnect with the same `session_id`: `session_snapshot` contains the interrupted assistant message.

Manual note in `uis/backoffice/README.md`: open `/knowledge`, send a question, send a second question before the first finishes, confirm the first bubble stays marked interrupted and the second answer is a new bubble. Reload and confirm the same thread returns.

## 6. PR answers

- Part 1 SSE only sends server events. This chat has to deliver tokens and accept `interrupt_requested` on the same connection while tokens are still arriving. That is a bidirectional channel.
- One producer on `chat.<session_id>` publishes to every subscriber queue. A second socket does not call the agent again.
- Abort cancels the HTTP stream and the generation task. LangGraph `interrupt()` is not used. The partial assistant message stays with `status` `interrupted`. The next text starts a new assistant turn and sets the session back to `active`.
