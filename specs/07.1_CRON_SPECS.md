# SPECS — 7.1 Nightly export + pipeline trigger (`job_runs`)

Independent **nightly worker**: export yesterday’s `telemetry_events` to CSV (audit backup), trigger the existing Milestone 6 pipeline as a **subprocess**, and record the attempt in **`job_runs`**. Lock = a `processing` row. Not FastAPI.

| Source | Role |
| --- | --- |
| Assignment (Background Processes) | Acceptance criteria, `job_runs` vs `pipeline_runs`, lock/idempotency |
| This file | Paths, CLI, schema, control flow, cron decision |
| [`data/pipelines/PIPELINE_DESIGN.md`](../data/pipelines/PIPELINE_DESIGN.md) | Pipeline CLI, month grain, `reporting.pipeline_runs` |
| [`services/api/telemetry/table.py`](../services/api/telemetry/table.py) | Source columns for the CSV |

**Out of scope:** changing KPI math, `/reporting` UI, `GET /telemetry/report`, `telemetry/analysis.py`, writes into `telemetry_events`, merging `job_runs` into `pipeline_runs`, APScheduler / FastAPI lifespan, a second lock table/column/flag.

## 1. Constraints (read first)

### 1.1 Vocabulary

| Kind | Required value |
| --- | --- |
| Script | `scripts/nightly_export.py` — `python scripts/nightly_export.py` from repo root |
| Job name | `nightly_export` (constant, not a generic `job`) |
| Status module | `services/jobs/job_runner.py` — **not** a FastAPI router |
| DDL | `services/jobs/schema.sql` + `ensure_job_runs_schema()` in `job_runner` |
| Statuses | `pending` → `processing` → `completed` \| `failed` only |
| CSV path | `data/raw/telemetry_YYYY-MM-DD.csv` (UTC `target_date`) |
| Pipeline subprocess | **This repo’s** CLI (not `telemetry_kpi_daily`): see §4.3 |

Generic names (`run_job.py`, `lock_flag`, `cron_status`) are not acceptable.

### 1.2 Isolation

| Leave untouched | Why |
| --- | --- |
| `services/api/telemetry/analysis.py`, `GET /telemetry/report`, `/telemetry` | Engineering report |
| Writes into `telemetry_events` | Export is read-only |
| `reporting.pipeline_runs` / ETL tasks | Pipeline owns those rows |
| `context/**`, `milestones/**`, `.github/**` | Protected |
| FastAPI `app/main.py` lifespan / routers | Worker must not run on the API thread |

`job_runner` may **reuse** `inventory.database` / `get_pipeline_engine()` for the same Postgres/SQLite URL. Do **not** mount a `/jobs` API. Do **not** import `nightly_export` from Uvicorn.

### 1.3 Two tables (do not merge)

| Table | Writer | Purpose |
| --- | --- | --- |
| `job_runs` | `scripts/nightly_export.py` via `job_runner` | Nightly orchestration: CSV + subprocess + lock + per-day idempotency |
| `reporting.pipeline_runs` | `monthly_clinic_supply_performance` only | ETL attempt (extract/transform/load, records_read/written) |

The script never inserts into `pipeline_runs`. The pipeline never inserts into `job_runs`.

### 1.4 CSV is a backup, not pipeline input

Export `telemetry_events` → `data/raw/telemetry_YYYY-MM-DD.csv` for audit/recovery. The pipeline still reads **`telemetry_events` via SQL**. Do not pass the CSV path into the subprocess. Do not rewrite `extract_month` to read the file.

### 1.5 PHI

Export only existing telemetry columns (`id`, `timestamp`, `service`, `event_type`, `level`, `value`, `message`, `tags`). No patient id, MRN, diagnosis, email, or incident `description`. `department` in tags is a clinical area, never a person.

## 2. Data model — `job_runs`

Same SQL engine as inventory/telemetry (`SUPABASE_DATABASE_URL`). Postgres: table `reporting.job_runs` (create schema if needed). SQLite fallback: table `job_runs` (same pattern as `reporting.pipeline_runs` in `data/pipelines/monthly_clinic_supply_performance/db.py`).

| Column | Type | Notes |
| --- | --- | --- |
| `id` | uuid / text | PK |
| `job_name` | text | Always `nightly_export` for this script |
| `target_date` | date | **Required.** UTC calendar day being exported |
| `status` | text | `pending` \| `processing` \| `completed` \| `failed` |
| `started_at` | timestamptz / text | Set when entering `processing` |
| `finished_at` | timestamptz / text | Set on `completed` or `failed` |
| `error_message` | text null | Exception message on `failed` only |
| `created_at` | timestamptz / text | Insert time |

**Index:** `(job_name, target_date)` — e.g. `ix_job_runs_job_name_target_date`. Not a unique constraint (failed retries may insert a new row).

Commit DDL in `services/jobs/schema.sql` (`CREATE TABLE IF NOT EXISTS` + index). `ensure_job_runs_schema()` runs it at process start (like `ensure_reporting_schema`). Do not use Alembic unless the repo already has it.

## 3. Status module — `services/jobs/job_runner.py`

Implement at least:

| Function | Behaviour |
| --- | --- |
| `ensure_job_runs_schema()` | Idempotent DDL |
| `has_processing_lock(job_name)` | `True` if **any** row for that `job_name` has `status='processing'` (any `target_date`) |
| `has_completed_for_date(job_name, target_date)` | `True` if a **completed** row exists for that pair |
| `create_run(job_name, target_date)` | Insert `pending`, return id |
| `mark_processing(run_id)` | `pending` → `processing`, set `started_at` |
| `mark_completed(run_id)` | → `completed`, set `finished_at` |
| `mark_failed(run_id, error_message)` | → `failed`, set `finished_at` + message |

**Lock = `processing` only.** No flock, Redis, extra column, or `locked` flag.

**Zombies:** every path that called `mark_processing` must call `mark_completed` or `mark_failed`. Catch `Exception`, `mark_failed` with `str(exc)` (redact connection URIs the same way inventory does if you have `redact_secrets`), log `ERROR`, re-raise or `sys.exit(1)`. No row may stay `processing` after the process exits from a handled failure.

## 4. Script — `scripts/nightly_export.py`

Shebang + `if __name__ == "__main__"`. From repo root:

```bash
python scripts/nightly_export.py
uv run python scripts/nightly_export.py
TARGET_DATE=2026-09-07 uv run python scripts/nightly_export.py
```

Add repo root and `services/api` to `sys.path` (same as `scripts/analyze.py` / `data/pipelines/paths.py`).

### 4.1 Resolve `target_date`

```text
TARGET_DATE env YYYY-MM-DD  →  that date
else                        →  datetime.now(timezone.utc).date() - timedelta(days=1)
```

Invalid `TARGET_DATE` → log ERROR and exit non-zero **before** taking the lock.

### 4.2 Control flow (this order)

```text
1. ensure_job_runs_schema()
2. target_date = resolve(...)
3. if has_processing_lock("nightly_export"):
     INFO log cancellation (job already processing) → exit 0   # silent abort, no new row
4. if has_completed_for_date("nightly_export", target_date):
     INFO log skipped as duplicate → exit 0                    # no CSV, no subprocess
5. run_id = create_run(...) ; mark_processing(run_id)
6. try:
     export_csv_if_missing(target_date)   # skip write if file exists
     run_pipeline_subprocess(target_date)
     mark_completed(run_id)
     INFO finish
   except Exception as exc:
     mark_failed(run_id, message)
     ERROR log
     raise / exit 1
```

`failed` for a date does **not** skip a later retry. Only `completed` is idempotent. If the CSV already exists from a crashed run, skip the write and still run the pipeline.

### 4.3 Export

- Window: `timestamp >= target_date 00:00:00+00` AND `timestamp < target_date + 1 day` (UTC).
- Path: `data/raw/telemetry_{target_date.isoformat()}.csv`. Create `data/raw/` if needed.
- If the file **exists**, do not overwrite (INFO: export already present).
- If missing: write header + rows (empty day = header only). `tags` as JSON text.
- Read-only on `telemetry_events`.

### 4.4 Pipeline subprocess

Do **not** use `python -m data.pipelines.telemetry_kpi_daily.run` — that module does not exist here.

```bash
# cwd = repo root; use the same interpreter
python data/pipelines/pipeline.py --month-start YYYY-MM-01 --no-sample
```

`YYYY-MM-01` = first day of the UTC month that **contains** `target_date` (nightly job still re-aggregates the month; destination upsert is already idempotent). `--no-sample` so a DB miss does not load fixtures.

Use `subprocess.run(..., check=True)` with `sys.executable` and repo-root `cwd`. Non-zero exit → exception → `failed`. Do **not** call `run_monthly_clinic_supply_performance()` in-process. Do **not** `POST /reporting/pipeline-runs`.

### 4.5 Logging

stdlib `logging`, INFO / ERROR. Every line includes **timestamp**, **`nightly_export`**, and **status** (or `skipped` / `cancelled` in the message). Examples: start (`processing`), finish (`completed`), duplicate skip, lock abort, exception (`failed`).

## 5. Trigger — do not use FastAPI

**Decision (document in the PR):** dedicated **Compose service** `nightly` for production-shaped deploys; **host crontab** one-liner for Codespaces/dev.

| Why | Why not |
| --- | --- |
| Separate container/process; cannot block Uvicorn | `APScheduler`, `@repeat_every`, lifespan hooks on `app.main` |
| Survives API reload; same `.env` / DB as `api` | In-process thread “worker” on the API |
| Host crontab is enough when Compose is not running | Installing a system cron inside the API image |

**Cron (UTC):** `5 2 * * *` — 02:05 UTC so “yesterday” is a closed calendar day.

```cron
# deploy/nightly.crontab (repo). Adjust REPO. Runs independently of uvicorn.
5 2 * * * cd /workspaces/jpetrucci49-ft-ai-engineering-2-company-project-monorepo && uv run python scripts/nightly_export.py >> /tmp/nightly_export.log 2>&1
```

Compose: new service (not a second Uvicorn). Same `env_file: .env`, mount repo `scripts/`, `data/`, `data/pipelines/` (or `HEALTHCORE_REPO_ROOT`). Command = cron daemon **or** a tiny loop that sleeps until 02:05 UTC and execs the script. Do **not** add the script to `npm run dev`.

Install crontab is **not** required in CI. Commit `deploy/nightly.crontab` + compose snippet + README note.
