# SPECS — 10.5 SSE notifications

Sales only sees a new RFP if someone reloads the operations dashboard. Push `rfp_ticket_created` the moment a ticket row is committed. No model calls. No agent runs.

Authoritative domain: [`context/10.5_CONTEXT.md`](../context/10.5_CONTEXT.md). Do not edit `context/**`. Field names already used by the RFP ticket stay as they are: `ticket_id`, `status`. Initial `status` is `analyzing`. The pipeline agent is `rfp_pipeline`. The flow is `rfp_workflow`. No patient identifier, diagnosis, draft text, PDF path, or handoff JSON in any event, log, or list payload.

**Out of scope:** `agent_step`, `agent_status_changed`, a second notification type, WebSockets, Redis, a new task store, and any change to intake, draft, or approval graph behavior.

**Read:** `services/api/rfp/service.py` (`create_ticket`), `services/api/rfp/router.py`, `uis/backoffice/components/dashboard/OperationsDashboard.tsx`, `packages/shared/auth/fetch.ts` (`authFetch`).

---

## 1. Event

Emit once, after `create_ticket` commits. Do not emit on later status changes.

```text
id: <monotonic int>
event: rfp_ticket_created
data: {"ticket_id":"<uuid>","status":"analyzing","agent_id":"rfp_pipeline","flow_type":"rfp_workflow"}

```

`event:` is required. Do not use the default `message` type. `data:` is one JSON object. `id:` increases by 1 per published event in this process.

Each open stream is its own queue. Publishing iterates those queues. One Uvicorn process is the fan-out. Fifty dashboards means fifty queues, not one shared socket. Bound each queue; if it is full, drop that connection rather than blocking ticket creation.

Keep-alive, every 15 seconds, is a comment frame (`: ping`) so clients do not treat it as a ticket.

## 2. HTTP

Same FastAPI app. Same JWT as the other `/rfp` routes (`get_current_user`). Missing or invalid token: **401**. Any authenticated backoffice user may listen. Do not require the manager role.

| Method | Path | Behavior |
| --- | --- | --- |
| `GET` | `/rfp/events` | SSE stream. Headers: `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `Connection: keep-alive`, `X-Accel-Buffering: no`. |
| `GET` | `/rfp/tickets` | Newest 20 tickets. Body: `{"tickets":[{"ticket_id":"","status":"analyzing"}]}`. Those two fields only. |

BFF, streaming the upstream body without buffering it into JSON:

- `GET /api/rfp/tickets`
- `GET /api/rfp/events`

The browser calls the BFF with `authFetch` (`Authorization: Bearer`). It does not call port 8000 and it does not use `EventSource`.

## 3. Dashboard

`OperationsDashboard` stays the billing, clinical, and people snapshot. Add a client child on `/` that does not replace those sections and does not refetch them when a ticket arrives.

The child:

1. `GET /api/rfp/tickets`, then open `GET /api/rfp/events` with `fetch` and read `ReadableStream`.
2. On `rfp_ticket_created`, prepend that ticket if `ticket_id` is not already shown.
3. Render a block titled **RFP tickets**, separate from the billing, clinical, and people cards. Each row shows `ticket_id` and the text **Needs processing** when `status` is `analyzing`. Other statuses show the status word only. Link the row to `/rfp`.
4. On disconnect, show **Reconnecting…** and keep the rows already on screen. Backoff is 1s, 2s, 4s, 8s, 16s, then 30s. A successful open resets the delay.
5. After each successful reconnect, `GET /api/rfp/tickets` again, merge by `ticket_id`, then resume the stream. SSE is only for tickets created after that refetch. The same `ticket_id` never renders twice.

Recovery is refetch-then-SSE. The ticket table is the record of tickets created while nobody was connected. Do not add a second replay log.

## 4. Tests

`tests/pipelines/test_rfp_sse.py`.

- `GET /rfp/events` without a token returns 401.
- With a token, response `Content-Type` contains `text/event-stream`. After `create_ticket`, the stream frame contains `event: rfp_ticket_created` and `data:` JSON with `ticket_id`, `status` `analyzing`, `agent_id` `rfp_pipeline`, and `flow_type` `rfp_workflow`.
- A ticket created with no subscriber is still returned by `GET /rfp/tickets`.

Manual check, written in `uis/backoffice/README.md`: open `/`, stop the API, upload a ticket from another session, start the API, confirm **Reconnecting…** clears and that `ticket_id` appears once.

## 5. PR answers

Record these in the PR, using the choices above:

- Two sales users each hold their own SSE connection. Fifty users are fifty in-process queues.
- Missed tickets are recovered by refetching `GET /rfp/tickets` on reconnect, then deduping on `ticket_id`.
- SSE fits a one-way “ticket registered” notice. A channel that also accepted approve or reject from the browser would need WebSockets.
