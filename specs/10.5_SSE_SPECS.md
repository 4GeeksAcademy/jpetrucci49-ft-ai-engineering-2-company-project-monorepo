# SPECS — 10.5 SSE notifications

Tom Callahan’s team only sees a new RFP if someone reloads the operations dashboard. Push `rfp_ticket_created` once, when intake has accepted the document and the ticket is still `analyzing`. No model calls beyond the intake run that already exists. Do not start another agent.

Authoritative domain: [`context/10.5_CONTEXT.md`](../context/10.5_CONTEXT.md). Do not edit `context/**`. Reuse RFP fields already on the ticket and its metadata. Do not invent names. No patient identifier, diagnosis, draft text, PDF path, section text, or handoff JSON in any event, log, or list payload. `client_name` is the institution.

**Out of scope:** `kpi_threshold_alert`, a chronic-care case event, WebSockets, Redis, a new task store, and any change to draft or approval behavior.

**Read:** `data/pipelines/rfp_intake/persist.py` (`persist_complete`, `_upsert_metadata`), `services/api/rfp/router.py`, `services/api/rfp/events.py`, `uis/backoffice/components/dashboard/RfpTicketFeed.tsx`.

---

## 1. When to emit

`create_ticket` inserts `status` `analyzing` before classification, with `rfp_id` null and no metadata. Do not emit there. A discarded ticket never emits.

Emit once inside `persist_complete`, after `_upsert_metadata` has set `rfp_id` and the metadata row, while `ticket.status` is still `analyzing`, and before that function sets `intake_complete`. Do not emit again on later status changes.

```text
id: <monotonic int>
event: rfp_ticket_created
data: {"ticket_id":"","rfp_id":"","client_name":"","client_country":"US","program_type":"occupational_health","status":"analyzing","created_at":"2026-07-24T14:32:00Z"}

```

`event:` is required. Do not use the default `message` type. `data` is one JSON object with those seven keys only. `created_at` is the ticket’s UTC timestamp. `client_country` is `US`, `UK`, or `unknown`. `program_type` is the stored value. `client_name` may be null. `id` increases by 1 per published event in this process.

Each open stream is its own queue. One Uvicorn process fans out. A full queue drops that connection so intake does not wait. Keep-alive every 15s is a comment frame `: ping`.

## 2. HTTP

Same FastAPI app. Same JWT as the other `/rfp` routes (`get_current_user`). Missing or invalid token: **401**. Any authenticated user may listen.

| Method | Path | Behavior |
| --- | --- | --- |
| `GET` | `/rfp/events` | SSE. `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `Connection: keep-alive`, `X-Accel-Buffering: no`. |
| `GET` | `/rfp/tickets` | Newest 20. Each item has the same seven fields as `data` above, and no others. |

BFF, streaming the upstream body without buffering it into JSON:

- `GET /api/rfp/tickets`
- `GET /api/rfp/events`

The browser calls the BFF with `authFetch`. It does not call port 8000 and it does not use `EventSource`.

## 3. Dashboard

`OperationsDashboard` stays the billing, clinical, and people snapshot. The **RFP tickets** block does not refetch those sections.

1. `GET /api/rfp/tickets`, then open `GET /api/rfp/events` with `fetch` and read `ReadableStream`.
2. On `rfp_ticket_created`, prepend that ticket if `ticket_id` is not already shown.
3. Each row shows `client_name` (or `ticket_id` when the name is null), `client_country`, `program_type`, and **Needs processing** when `status` is `analyzing`. Other statuses show the status word only. Link the row to `/rfp`.
4. On disconnect, show **Reconnecting…** and keep the rows. Backoff is 1s, 2s, 4s, 8s, 16s, then 30s. A successful open resets the delay.
5. After each successful reconnect, `GET /api/rfp/tickets` again, merge by `ticket_id`, then resume the stream. The same `ticket_id` never renders twice.

Recovery is refetch-then-SSE. The ticket table is the record of tickets accepted while nobody was connected.

## 4. Tests

`tests/pipelines/test_rfp_sse.py`.

- `GET /rfp/events` without a token returns 401.
- With a token, `Content-Type` contains `text/event-stream`. After a ticket is accepted (`persist_complete` / equivalent), the frame contains `event: rfp_ticket_created` and `data` with `ticket_id`, `rfp_id`, `client_name`, `client_country`, `program_type`, `status` `analyzing`, and `created_at`.
- A ticket that is discarded, or accepted while nobody is listening, is still listed by `GET /rfp/tickets` with those seven fields. A discarded ticket is not an SSE event.

Manual check in `uis/backoffice/README.md`: open `/`, stop the API, accept a ticket from another session, start the API, confirm **Reconnecting…** clears and that ticket appears once.

## 5. PR answers

- Two sales users each hold their own SSE connection. Fifty users are fifty in-process queues.
- Missed tickets are recovered by refetching `GET /rfp/tickets` on reconnect, then deduping on `ticket_id`.
- SSE fits a one-way “ticket accepted” notice. A channel that also accepted approve or reject from the browser would need WebSockets.
