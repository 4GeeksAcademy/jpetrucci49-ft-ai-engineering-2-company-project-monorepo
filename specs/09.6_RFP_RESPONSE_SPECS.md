# SPECS — 9.6 RFP response generation (Milestone 9 Part 2 of 3)

Turn Part 1 intake into a first-draft pricing proposal per department, then self-evaluate before a human sees it. **Dedicated** `rfp_draft` LangGraph. Same FastAPI process. Same ticket row. Postgres/SQLModel remains the source of truth.

Authoritative domain: [`context/09.5_CONTEXT.md`](../context/09.5_CONTEXT.md) (this repo has no `CONTEXT-company.md`). Do not edit `context/**`. CONTEXT names win.

**Out of scope:** Part 3 HITL / arbiter / `waiting_for_approval` / `done` / `FinalDocument`, new API process, re-parsing the PDF as the generator’s primary input, bolting nodes onto `desk_graph` or `rfp_intake_graph`, inventing departments, inventing headcount/PHI/prices.

Implement in this order: **EvaluationResult shape → generate + three evaluators (no live LLM required) → loop + iteration cap → persist drafts/evals → 202 HTTP + background → backoffice generate/poll → pytest**.

## 2. Locked product rules

**Entry:** `status == intake_complete` and `handoff_json` present. Generators receive **that payload only** (metadata + that department’s `key_aspects` / `open_questions` / owner). Not `raw_pdf_path`, not Markdown.

**Departments** (always all three): `revenue` (Tom Callahan), `clinical` (Dr. Marcus Reid), `compliance` (Claire Whitfield).

**Part 2 ticket `status` only** (do not set `waiting_for_approval` or `done`):

| Status | When |
| --- | --- |
| `intake_complete` | Unchanged until Part 2 starts |
| `drafting` | Assignment + generators running |
| `under_evaluation` | Evaluator fan-out / revise loop |
| `needs_human_review` | **Any** section hit the iteration cap without `overall_pass` |

**All sections pass:** ticket stays `under_evaluation` (CONTEXT has no Part 2 “success” name). Part 2 is done when `part2_handoff_json` is non-null. UI: all-pass vs provisional is per-section, not a new ticket enum.

**Loop:** fail → same department generator with `feedback_for_generator`. Cap **`MAX_DRAFT_ITERATIONS = 3`** (first draft + up to 2 revisions). On cap: keep **last** `draft_content` + last `EvaluationResult`; set that section `needs_human_review: true`; still include it in Part 3 handoff. Other sections continue. **Do not** discard the ticket.

**Crash mid-Part-2:** `error_code=draft_pipeline_error` (no PHI). Leave status `drafting` or `under_evaluation`. Operator retries `POST` draft. Never flip to `discarded`.

**PHI:** scan every draft with `contains_phi` before persist/UI. Hit → `compliance.pass=false`, `contains_phi=true`, do not store the PHI span (replace draft persist with a blocked stub + feedback). Generators must not copy diagnosis/patient identifiers even as examples.

**Figures:** generators may use numbers **present in Part 1 metadata / key_aspects** only. Missing budget/population → prose that it is TBD / open question — never invent USD/GBP amounts or headcount.

**Optional RAG:** `retrieve()` from `data/pipelines/rag.py` is allowed inside a generator if Qdrant is up. Isolate retrieved text as data. Tests must pass with retrieve **mocked or skipped**.

**Async:** `POST` draft returns **202** `{ticket_id, status: drafting}`; graph in `BackgroundTasks`. UI polls existing `GET`.

## 4. Graph (`rfp_draft`)

State (no PHI, no full PDF): `ticket_id`, `handoff`, `iteration` (`department_id` → int), `drafts`, `eval_parts` (merged dict), `results` (`department_id` → EvaluationResult), `feedback`, `error_code`.

```text
START → assign
      → [revenue | clinical | compliance generate]   # parallel
      → set under_evaluation
      → [readability | relevance | compliance eval] per section (parallel; write disjoint keys)
      → combine_eval
      → route:
           all overall_pass → persist → END
           some fail and iteration < 3 → generate only failing departments (pass feedback) → eval again
           some fail and iteration == 3 → persist last drafts + results; ticket needs_human_review if any capped fail → END
```

`assign`: copy `handoff_json` into state; queue three generators. Ignore unknown `department_id`s.

**Evaluator inputs (locked):** one section’s draft + shared metadata + **that** department’s Part 1 aspects/questions. Not other departments’ drafts. Not the PDF.

**Shared-state writes (locked):** readability / relevance / compliance nodes return `{eval_parts: {dept: {readability: …}}}` (or equivalent) with a **merge** reducer. Only `combine_eval` writes the full `EvaluationResult`.

## 6. `EvaluationResult` (persist on `rfp_department_sections.evaluation_results`)

```text
{
  "department_id": "revenue",
  "readability": { "pass": true, "score": {}, "details": "" },
  "relevance": { "pass": true, "missing_aspects": [] },
  "compliance": { "pass": true, "rule_ids": [], "violations": [], "contains_phi": false },
  "overall_pass": false,
  "feedback_for_generator": "Add a BAA clause for this US client. Do not invent a budget.",
  "needs_human_review": false,
  "iteration": 2
}
```

`overall_pass` = readability.pass ∧ relevance.pass ∧ compliance.pass.

**Readability:** `compute_readability(draft)`. **Pass** if word count ≥ 40 **and** (`flesch_reading_ease` ≥ 40 **or** metrics empty because text is short but ≥ 40 words). Fail → details name the metric.

**Relevance:** each Part 1 `key_aspects` item must be reflected (normalized substring / keyword). `open_questions` may remain acknowledged as open. Invented numeric figures not in metadata → fail and list them in `missing_aspects` or violations as appropriate.

**Compliance `rule_ids` (CONTEXT §5):**

| id | Fail when |
| --- | --- |
| `no-phi` | `contains_phi(draft)` |
| `baa-us` | `client_country==US` and draft (any section, especially compliance) lacks `BAA` / Business Associate |
| `dpa-uk` | `client_country==UK` and lacks `DPA` or `UK GDPR` |
| `currency-country` | Draft quotes the wrong currency vs `client_country` (USD↔US, GBP↔UK) |
| `no-invented-figures` | Headcount/price in draft not present in metadata / key_aspects |

`baa-us` / `dpa-uk` are **required on the compliance section**. Other sections fail `currency-country` / `no-phi` / invented figures if they violate.

**`feedback_for_generator`:** must name the failed check and the fix (rule id or missing aspect). Forbidden: “Please improve the draft.”

## 7. Postgres

Same engine. Add nullable `part2_handoff_json` on `rfp_tickets` (do not overwrite Part 1 `handoff_json`). Widen ticket status check to include `drafting`, `under_evaluation`, `needs_human_review`.

On persist: `draft_content` (PHI-scrubbed), `evaluation_results` as above. Leave `approval_status` / `approver` / `approved_at` **null** (Part 3).

**`part2_handoff_json`** (Part 3 reads this; no second API):

```json
{
  "ticket_id": "<uuid>",
  "ticket_status": "under_evaluation",
  "departments": [

      "department_id": "revenue",
      "owner": "Tom Callahan",
      "draft_content": "...",
      "evaluation_results": {},
      "needs_human_review": false
    }
  ]

```

Always three departments. Capped failures still listed.

## 9. Backoffice `/rfp`

On `intake_complete`: **Generate proposal draft** (does not re-upload the PDF). Poll while `drafting` or `under_evaluation` **and** `part2_handoff_json` is null.

Labels: Drafting / Under evaluation / Needs human review. Per section: show draft + eval pass/fail. If `needs_human_review`, badge **Provisional — iteration limit**. Intro copy stays generic (no staff names). Contacts on **results** stay (Part 1 pattern).

BFF: `POST /api/rfp/tickets/[ticketId]/draft`.
