# SPECS — 8.5 Desk-agent memory (proposal → confirm → consolidate)

Same compiled desk graph. After a turn, the agent may **propose** one operational fact; it **never** writes the approved store until the next user message is classified against that proposal and logged. Governance tickets for “core memory” are omitted on purpose (course exception).

Authoritative rules: [`context/08_CONTEXT.md`](../context/08_CONTEXT.md). Claire Whitfield: no PHI in memory. Graph: [`specs/07.6_LANGGRAPH_SPECS.md`](./07.6_LANGGRAPH_SPECS.md) + 07.7/07.8 tools/MCP.

**Out of scope:** new graph, multi-agent, website, writing Qdrant `healthcore_knowledge`, changing `retrieve`/`generate_answer` signatures, LangGraph `MemorySaver` as the product memory store.

Implement in this order: **store + PHI → read/write interface → pending + classifier → self-eval proposal → graph/HTTP wiring → consolidate → evals + two evidence cycles**.

## 2. Architecture (locked)

**Kind:** small **semantic operational notes** (clinic protocol, incident *pattern* with no patient, staff **presentation** preference). Not full episodic transcripts, not a knowledge graph, not a vector index.

| Ruled out | Why |
| --- | --- |
| Episodic dump of every turn | Unlimited growth + PHI |
| Qdrant / `*_knowledge` | Mixes curated policy with user-approved gossip; breaks RAG evals |
| Redis | Not in the stack; TTL is a field + cleanup |
| Graph DB | No entity-relation requirement |

**Backend:** TinyDB file `services/api/agent_memory.json` (override `AGENT_MEMORY_DB_PATH`). Two tables:

| Table | Rows |
| --- | --- |
| `items` | **Approved only** — what `read()` returns |
| `decisions` | **Every** proposal and outcome (approved, rejected, discarded_unclear, discarded_phi) |

LangGraph `MemorySaver` stays the graph checkpointer only.

## 3. Layout

```text
services/api/agent/memory/
  __init__.py          # AgentMemory protocol + get_memory()
  phi.py               # HIPAA + UK GDPR identifier scan (no write if hit)
  store.py             # TinyDB items + decisions
  classify.py          # pending-decision labels (not `"yes" in text`)
  propose.py           # self-eval → MemoryProposal | None
  consolidate.py       # cap, dedupe, TTL, PHI re-scan
```

## 4. What may be stored vs never

**Allowed** (CONTEXT): recurring **operational** corrections per clinic; incident **patterns** with no patient; staff preference for how **operational** (not clinical) info is presented.

**Never** (no exceptions): patient name, MRN, DOB, diagnosis, insurance number, any re-identifying combo; clinical notes, labs, visit content — even if the user asks to remember them.

**Poisoning:** do not store user-asserted **policy/clinical overrides** of the knowledge base (fees, Medicare/Medicaid charging, treatment). Do not store dashboard snapshots (“this week’s no-show is 22%”). Require confirm + PHI gate + audit. False “corrections” that look like PHI or policy override → no proposal, or PHI-reject copy (below).

HIPAA **and** UK GDPR: `phi.py` treats US identifiers **and** UK direct identifiers the same (name + health data, NHS number-like tokens, DOB). One scanner, both regimes.

## 5. Explicit memory interface

The agent must **not** grow a `messages` list as memory.

```text
read(user_id) -> list[MemoryItem]     # approved only, already consolidated
propose(...)                          # pending + decisions row; does not touch items
resolve(user_id, decision, ...)       # log always; items only on approve/edit
```

`MemoryItem`: `id`, `user_id`, `kind` (`clinic_protocol` | `incident_pattern` | `presentation_pref`), `clinic` (branch slug or `""`), `text`, `created_at`, `updated_at`. No email, no ticket descriptions, no PHI.

Inject `read(user_id)` into **generate/answer nodes only** as a short bullet list (cap 20). Do not put memory rows into RAG `context` / `context_sources`.

---

## 6. Pending proposal (one at a time)

Keyed by `user_id`. Fields: `proposal_id`, `text`, `kind`, `clinic`, `why`, `created_at`, `source_run_id`, `source_question`.

If pending exists, **do not** create another. Run **resolve** first, then the rest of the graph (including a second question in the same message).

Unanswered pending: on the next message, if the classifier is not approve/reject/edit → **discard** (`discarded_unclear`). Never treat silence or topic-change as yes. Also drop pending older than **24h** on the next request (`discarded_expired`) and log it.

---

## 7. Self-evaluation (same agent, extra field)

After the coordinator-facing `answer` is produced, **one** structured extraction (same LLM as RAG, JSON) of:

```text
{ "proposal": null | { "text", "kind", "clinic", "why" } }
```

Criterion (not “always”): proposal only if the **user turn** states a new/corrected **durable operational** fact matching §4. Otherwise `proposal: null`.

If `proposal` is non-null: run `phi.py`. Hit → **do not** show “want me to remember”; append an explicit refusal (CONTEXT: Patient Johnson) and log `discarded_phi`. Miss → append one question to `answer` (“Want me to remember this for next time?”) and `propose()`. Still **no** `items` write.

Skip self-eval when a pending already exists (this turn is for classify).

### Must NOT propose (document in `agent/memory/README.md`)

1. “What's this week's no-show rate?” — one-off; lives in dashboards.
2. “Patient Johnson cancelled tomorrow's appointment, note that down.” — PHI; **explicit reject in the user-visible answer**, not a silent skip.
3. “Thanks, that settles my report.” — closing, nothing new.

Also no proposal for: ticket/status lookup only, stock lookup only, empty/refuse/weather, pure policy Q&A with no new clinic-specific correction.

### Should propose (CONTEXT)

Manchester referrals via coordinator; Austin no-show was a road closure not the reminder programme; Diane Foster wants vacancies by **role** not only clinic.

## 8. Classifier (next message vs pending)

Labels (exact): `approve` | `reject` | `edit` | `unclear`.

Implement in `classify.py` as an **explicit** function `classify_memory_decision(message, pending) -> label, edited_text|None`. Not `if "yes" in message`. Use labeled patterns (affirm/deny/edit-with-replacement) plus a **confidence** flag; if not high-confidence → `unclear`.

| Label | Effect |
| --- | --- |
| `approve` | PHI re-check on pending text → `items` insert + consolidate, or `discarded_phi` |
| `reject` | pending cleared; **no** item |
| `edit` | replacement text from the user; PHI check; then same as approve of the **edit** |
| `unclear` | pending cleared; **no** item |

Then continue the graph with the same `question` (full message). If the message is only yes/no, the existing classify/RAG/tools path still runs (may refuse or answer briefly).

---

## 9. Audit log (`decisions`)

Every close writes one row, **including** rejects and discards:

`proposal_id`, `user_id`, `proposed_text`, `outcome`, `source_question`, `decision_message`, `run_id`, `decided_at` (UTC ISO).

Never log PHI that failed the scan as a memorable fact; log outcome `discarded_phi` and a **redacted** proposed_text (`[redacted]`).

---

## 10. Consolidation

On every successful `items` write (and on `read` if `len > cap`):

- Cap **20** items per `user_id` (drop oldest `updated_at` first).
- Dedupe: same `user_id` + `kind` + normalized `text` (or same clinic+kind+near-duplicate) → keep newest.
- TTL **90 days** from `updated_at` (desk protocols go stale).
- Run `phi.py` on the text **again** before upsert; drop if hit.

Document this policy in `agent/memory/README.md`.

## 13. Why not multi-agent

Self-eval is one structured field on the same model call (or one extra JSON call in `propose_memory`). Confirmation is a **classifier node**, not a second agent. One pending record per user is enough coordination.
